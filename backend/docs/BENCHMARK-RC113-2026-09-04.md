# RC113 benchmark record — 2026-09-04

Measured on the actual repository data at commit `a8b6b004cc6aa736a315105e183810356f36645c` (`2026.09-static-v5-rc113`), not a fixture.

- Host: Windows `amd64`, 32 logical CPUs, Go `go1.26.3`, local D: filesystem.
- API command: `go -C backend run ./cmd/evo-bench -data-root .. -rounds 20 -concurrency 16`.
- The harness uses Go's loopback `httptest` server and consumes every response body. `startupLoadMs` measures snapshot construction after the process begins; it is not a full executable launch measurement. Heap values are Go heap metrics, not OS RSS.
- Full inventory command: `go -C backend run ./cmd/evo-index -data-root .. -out index/bench-current.json`, measured wall time 14.6074887 s for 5,027 files and 906,062,153 bytes. The temporary output was removed after the measurement; the command's atomic rename behavior was exercised.
- `cold routed search` is the first `perissodactyla` request and includes reading/decompressing and building the typed prefix index for the routed COL shard. `warm routed search` is the following 20 requests. `mixed concurrent` is 16 workers × 20 requests, alternating entity evidence and the same search.

At the end of the run, Go reported `heapAllocBytes=72,479,080` and `heapInuseBytes=87,531,520`; the loaded search shard and bounded cache account for the memory footprint after the approximately 61 ms snapshot load. Response bytes are the aggregate bodies consumed for each sample. `0 ms*` means below the millisecond conversion precision used by this first harness, not zero physical time.

The result demonstrates the intended cold/warm difference and routed-shard behavior on RC113. It is not a claim of absolute best performance, production capacity, or scientific completeness. Re-run on target Android/iOS hardware and an external HTTP deployment before using device or network capacity numbers.
